# LiveTranslate 端侧化与省电调研

> 2026-10-11 ｜ 触发问题：加载慢、耗电（100W USB-C 供电下电量不升反降，dGPU 占用 ~40%）、打包体积大

---

## 0. 结论先行

1. **先纠正一个前提**：项目当前跑的不是 Whisper `small`，而是 **FunASR `SenseVoice-Small`（234M 参数）+ CUDA**（`user_settings.json` 里 `asr_device = "cuda:0"`）。SenseVoice-Small 本身就是 FunASR 模型名里的 "Small"，容易和 Whisper 的 `small` 档位混淆。**这一点决定了后面所有判断**。

2. **费电的根因不是"模型大"，是"独显被唤醒了"**。RTX 4060 Laptop 只要被任何进程占用（哪怕 40%），显存频率就会拉满、整卡进入 18W 起步的工作态，推理时 40–60W。**省电的第一优先级是"不碰 dGPU"，而不是"让 GPU 跑得更省"**。

3. **中文场景下没有"更轻且质量不低"的替换模型值得换**。SenseVoice-Small(234M) 已经是质量/体积的甜点；Paraformer-Large(220M) 与它同量级但精度更低。**真正的收益来自换「运行时」**（PyTorch+CUDA → ONNX Runtime），不是换模型。

4. **打包体积可以从 ~2.5 GB 降到 ~250 MB（约 1/10）**：`sherpa-onnx`(2.2MB) + `onnxruntime`(14.2MB) + SenseVoice int8 模型(229MB)。

5. **推荐路线**：本地 CPU 推理（sherpa-onnx + SenseVoice int8）为主，**远程 ASR**（项目已有）作为"极致省电"选项。不建议继续用 GPU。

## 2. 三个症状的根因

### 2.1 加载慢

冷启动成本拆开看（此前实测）：

| 环节 | 耗时 | 说明 |
|---|---|---|
| PyInstaller one-file 解包 | 与包体成正比 | **每次启动**都要把 ~2.5GB 写到临时目录 |
| `import torch` | ~4.7 s | CUDA DLL 加载 |
| `import funasr` | 10–14 s（已从 31.9s 优化） | 见 `asr/funasr_boot.py`，已挡掉 432 个子模块的 eager import |
| `AutoModel()` 构造 | 4–6 s | 权重加载 |
| 首次 `generate` | <1.5 s | 预热 |

**结论**：慢的是 three 个叠加项——**one-file 解包 + torch import + funasr import**。换成 onnxruntime 后，torch 和 funasr 两项**直接消失**，onnxruntime 的 import 是百毫秒级。

### 2.2 费电（核心）

**机制**：NVIDIA Optimus 混合模式下，dGPU 平时处于 P8 低功耗态（RTX 4060 约 1–2W）。**只要有任何进程创建了 CUDA context 并持续占用，它就不会回到低功耗态**——实测有用户报告 4060 Laptop 在"占用率 0%"时依然核心 2250MHz / 显存 8000MHz / **功耗 18W**（显存频率被拉满是关键，显存是独立供电域）。推理负载下整卡 40–60W。

**功耗账**（推断，需实测校准）：

| 项 | 估算 |
|---|---|
| dGPU（40% 占用） | 40–60 W |
| CPU（VAD + 音频重采样 + Qt 渲染 + Python） | 15–25 W |
| 屏幕 + 主板 + 内存 + 外设 | 15–25 W |
| **合计** | **70–110 W** |

100 W USB-C PD 输入 ≤ 峰值整机功耗 → **电量不升反降**完全说得通。

> **关键结论**：不需要"降低 GPU 占用"，需要"**让 GPU 完全不被占用**"。只要 ASR 跑在 CPU（或远端），dGPU 就会长期留在 1–2W 的 P8 态。

### 2.3 体积

one-file 里的大头是 **torch + CUDA runtime + torchaudio + funasr + transformers**。`build_exe.py` 的注释里已经写了：光 `torch/*.lib` 静态库就有 ~780MB（`dnnl.lib` 一个 623MB）——虽然已经排除了 `.lib`，但**运行时 DLL（cuDNN/cuBLAS/cuFFT…）本身就是 GB 级**。

## 3. 模型选型：中文为主，还有更轻的吗？

按参数量 / 量化体积 / 中文精度整理（数据来源见文末链接，**不同测试集不可严格横比**）：

| 模型 | 参数量 | int8 体积 | 中文 CER（越低越好） | 流式 | CPU 可跑 | 备注 |
|---|---|---|---|---|---|---|
| streaming-zipformer-small-ctc-zh | （小） | **20.3 MB** | 一般 | ✅ 真流式 | ✅ | 极致的轻，精度折扣大 |
| **Paraformer-Large** | 220M | 237 MB | 9.85–10.18% | ❌ 需 VAD | ✅ 15× 实时 | 最轻的"工业级"中文 |
| **SenseVoice-Small（现用）** | 234M | **229–254 MB** | **7.8–8.01%** | ❌ 需 VAD | ✅ 17× 实时 | 多语种 + 情感/事件标签 |
| streaming-zipformer-zh-int8 | （大） | 160 MB | 中 | ✅ 真流式 | ✅ | 2025-06-30 版，中英双语分支更大 |
| Moonshine-tiny | 27M | — | **中文未公开** | ✅ | ✅ | 英文为主，中文暂不适用 |
| Qwen3-ASR-0.6B | 600M | — | —（RTF 0.0092） | ✅ | 勉强 | 2026-01 开源，偏重 |
| Fun-ASR-Nano | 800M | 551MB(q5K)+470MB encoder | 8.25–8.30% | ✅ | 6× 实时 | **比 SenseVoice 重得多**，不省电 |
| FireRedASR-AED | 1.1B | — | **3.18%（最强）** | ❌ 限 60s | GPU | 精度第一梯队，但门槛高 |
| FireRedASR-LLM | 8.3B | — | — | — | ❌ | 32GB 显存起步 |
| Whisper small（faster-whisper） | 244M | ~250 MB | **22.12%（whisper.cpp）** | ❌ | 慢 | 中文比 FunASR 差约 3 倍 |

**几个关键判断**：

- **SenseVoice-Small 是当前的甜点，换模型得不到什么**。换成 Paraformer-Large 是同量级但更差；换成 Fun-ASR-Nano 更重更耗电；换成 FireRedASR 精度上去了但彻底告别端侧。
- **⚠️ SenseVoice 被官方标记"即将停用"**：阿里百炼平台文档已把 SenseVoice 标注为 *soon to be discontinued*，引导迁移到 Fun-ASR / Paraformer-v2。FunASR 仓库本身仍在维护 SenseVoice 的推理，**短期无忧，但中长期要有迁移预案**。
- **SenseVoice 没有原生流式**，sherpa-onnx 是靠 "VAD + 分块离线推理" 模拟。对"实时字幕"场景，**如果嫌延迟，才需要考虑流式 Zipformer**；否则 SenseVoice + VAD 分块已经完全够用（当前的实现就是这条）。
- **Whisper 系列在这个场景可以彻底放弃**：中文精度约为 SenseVoice 的 1/3，没有理由再留。

## 4. 优化方案

### 路线 A：本地 CPU + ONNX Runtime（sherpa-onnx）——**推荐**

| 组成 | 体积 |
|---|---|
| `sherpa-onnx`（Python 绑定） | 2.2 MB |
| `onnxruntime`（CPU） | 14.2 MB |
| SenseVoice int8 模型（`model.int8.onnx` + `tokens.txt`） | 229 MB |
| **合计** | **≈ 245 MB** |

- **零 torch / 零 CUDA / 零 funasr / 零 modelscope / 零联网**。模型下完后整条链路不联网（也解决了 FunASR 启动时连 modelscope 校验的老问题）。
- 模型权重**与现在完全相同**（同一个 SenseVoiceSmall，只是转成了 int8 ONNX）→ **中文质量预期不降反略升**（量化后 CER 实测 8.01% → 7.99%）。
- CPU RTF ≈ 0.1（约 10× 实时），足够支撑实时字幕。
- **dGPU 完全不唤醒** → 功耗回落到 25–40W 量级。
- `build_exe.py` 已经预留了 sherpa_onnx 的 DLL 收集，接上即可。
- 需要把 `SenseVoiceEngine` 的 `transcribe()` 换成 `sherpa_onnx.OfflineRecognizer`，接口是 `create_stream / accept_waveform / decode_stream`，与现有 `transcribe(audio) -> {text, language}` 一一对应，**改动局限在一个 backend 模块内**。

**风险点**：int8 CPU 推理的实测 RTF 与延迟必须在真机测（见第 6 节）；多线程 `num_threads` 要调（4 线程是常见起点）。

### 路线 B：FunASR 官方 llama.cpp / GGUF 运行时——**最"单文件"**

2026-06 官方发布，等价于"FunASR 版的 whisper.cpp"：

- **单个静态可执行文件，无 Python、无 GPU、无 CUDA**，内置 FSMN-VAD 和 detokenizer。
- 量化体积：SenseVoice q8 **254 MB** / f16 470 MB；Paraformer q8 237 MB。
- 官方 184 集中文测试集：**SenseVoice CER 8.01%**，而 whisper.cpp small 是 22.12%。
- CPU 速度：SenseVoice-Small **17× 实时**（比 whisper-large-v3 在 GPU 上的 13× 还快）。
- Windows 有预编译包（`funasr-llamacpp-windows-x64-vulkan.zip` / `-cuda.zip`）。

**优点**：体积最小、无任何 Python 依赖、可脱离 Python 分发。
**缺点**：它是 CLI/文件导向的，**接入当前 Python GUI 需要走 subprocess + 管道**，实时流式改造量大于路线 A。适合"以后想彻底把 ASR 做成独立进程"时再上。

### 路线 C：远程 ASR（项目已有）——**最省电**

`livetranslate/asr/backends/remote.py` + `asr_server.py` 已经可用：ASR 跑在另一台机器，本机只做音频采集 + 字幕渲染。

- 本机 ASR 负载归零 → dGPU 永不唤醒，本机功耗压到最低。
- 机房里那台 `192.168.102.24` 就是天然的 host。
- 代价：依赖网络（局域网延迟通常可接受），且需要远端机器常开。

> 如果目标是"笔记本上长时间看视频不插电也扛得住"，**C 是功耗最低的解**；如果目标是"单机自包含"，**A 是平衡点**。

### 打包体积对比

| 方案 | 引擎+运行时 | 模型 | 打包总量 | GPU |
|---|---|---|---|---|
| 现状（PyTorch + CUDA + funasr） | **~2.5 GB** | 897 MB（项目内，不进包） | **~2.5 GB** | 常驻占用 ❌ |
| PyTorch CPU 版（最小改动） | ~800 MB | 同上 | ~800 MB | 不占用 ✅ |
| **A：sherpa-onnx + onnxruntime** | **16.4 MB** | 229 MB | **~245 MB** | 不占用 ✅ |
| B：llama.cpp 单文件 | 数 MB + 254MB 模型 | 含在内 | **~260 MB** | 不占用 ✅ |
| C：远程 | ~1 MB（httpx） | 0（在远端） | **~1 MB** | 不占用 ✅ |

> 注意：**模型放包外**（首次运行下载，或随包放 `models/`）比塞进 exe 更好——one-file 每次启动解包的代价与包体成正比，模型进包会让"启动慢"雪上加霜。

### 附带的省电细节（可与上面任一路线叠加）

1. **Windows 图形设置**把 `python.exe` / `LiveTranslate.exe` 显式指定为"节能（核显）"，避免被误调起 dGPU。注意：`onnxruntime` 的 CPU provider 不会碰 GPU；但如果装了 `onnxruntime-gpu`，它会拿 CUDA —— **CPU 路线就必须用 CPU 版 wheel**。
2. **限制 `num_threads`**：CPU 推理线程数不是越多越好，8 线程满跑会让 CPU 包功耗顶上去。建议 2–4 线程起步，实测调优。
3. **`torch.set_num_threads()`** —— 若仍保留 torch（如未来兼容 Whisper 后端），要显式限线程。
4. **笔记本电源计划**：不用"高性能"，用平衡/节能。
5. **`nvidia-smi` 观察**：跑起来后确认 dGPU 的 P-state 回到 P8、功耗 <5W，作为省电是否生效的验收标准。

## 5. 推荐路线（分阶段）

| 阶段 | 动作 | 收益 | 风险 |
|---|---|---|---|
| **P0（先验证）** | 真机实测：① `cuda:0` → `cpu` 后的 CPU 占用 / 延迟 / dGPU 功耗；② `sherpa-onnx + SenseVoice int8` 的 RTF | 用数据决定后续 | 无（只测不改） |
| **P1** | 新增 `asr/backends/sherpa_onnx.py`，作为第二个中文后端并列（不删现有） | 体积 → 250MB；dGPU 归零 | 改动局限在 backend + registry 一行 |
| **P2** | 打包切换到"CPU-only 发行"（可另出一个 lite 版），模型外置 | one-file 启动变快 | 需处理模型分发 |
| **P3（可选）** | 若嫌延迟：加流式 Zipformer 选项（`sherpa-onnx-streaming-zipformer-zh-int8-2025-06-30`，160MB） | 真流式低延迟 | 精度低于 SenseVoice |
| **P4（可选）** | 远程 ASR 作为"省电档"，UI 里一键切换 | 本机近似零负载 | 依赖网络 |

**不建议**：继续用 GPU 跑 SenseVoice。它是"用 10 倍功耗换 1 个数量级的延迟余量"，而当前场景**根本用不到那个余量**（实时字幕只需要快于实时即可，CPU 的 10–17× 已经远超）。

## 6. 实测结果（2026-10-11 完成）

测试工具：**`tools/bench_asr_backends.py`**（可复用：`--only gpu|cpu|sherpa`、`--audio <path>`、`--offsets 60,600,...`、`--threads 2,4,8`）。

测试素材：**真实课堂实录** `教育学-第一章-第一节-2.mp3`（68.4 分钟，教师招聘培训课），在 5 个采样点（60s / 600s / 1800s / 3000s / 3900s，覆盖开场到 65 分钟）各取 **8 秒**——8 秒正是 `max_speech_duration`，即管道会送去识别的最长片段。

### 6.1 延迟（RTF = 耗时 / 音频时长）

| 后端 | 加载 | @60s | @600s | @1800s | @3000s | @3900s | 8s 中位耗时 |
|---|---|---|---|---|---|---|---|
| PyTorch CUDA fp16 | 12.3 s | 0.012 | 0.012 | 0.012 | 0.011 | 0.013 | ~95 ms |
| PyTorch CPU **fp32** | 1.9 s | 0.072 | 0.065 | 0.065 | 0.067 | 0.068 | **~530 ms** |
| **sherpa-onnx int8 · 4 线程** | 1.9 s | 0.026 | 0.026 | 0.028 | 0.027 | 0.027 | **~215 ms** |
| **sherpa-onnx int8 + 标点模型** | **2.3 s** | — | — | — | — | — | **~230 ms** |

关键点：

- **sherpa int8 在真实素材上高度稳定**（210–223 ms），因为耗时只取决于音频长度，与内容无关。
- **PyTorch CPU fp32 的最坏值达到 594 ms**（@60s 点），**已经贴到 600 ms 的 `interim_interval` 上**——这条"只改 device"的路不可靠。
- **sherpa + 标点的最坏值是 239 ms**，对 600 ms 预算有 **2.5 倍余量**。
- **标点模型只增加约 15 ms**（11–20 ms），几乎免费。

### 6.2 最坏情况背压测试

每 0.6 s 送满 8 s 音频、连打 25 轮（即管道永远来不及的理想化最坏输入）：

| 线程数 | 最坏单次 | 累计背压 | 判定 |
|---|---|---|---|
| 4 | 256 ms | **−9282 ms** | ✅ 每轮反而空闲约 370 ms，绝不累积 |
| 8 | 263 ms | −9516 ms | ✅ |

### 6.3 GPU 功耗（本机唯一可信的一手证据）

| 状态 | P-state | 功耗 | GPU util |
|---|---|---|---|
| 建 CUDA context / 推理中 | **P0** | **20.9 W** | **39 %** |
| 只用 CPU（PyTorch 或 sherpa） | **P8** | **2.5–3.3 W** | 0 % |

> **`39%` 正是最初报告里"4060 占用 40%"的来源。** 只要不碰 CUDA，dGPU 稳定停在 **P8 / ~2.7 W**，与 P0 / 20.9 W 相差约 **7.7 倍**。

⚠️ **两点必须说明**：
1. 早前单独运行 sherpa 时曾看到 P0 / 19 W（没有创建 CUDA context）——那是**上一个进程 CUDA 状态的残留**，同一进程内连续测时不会出现。所以判断"切 CPU 后是否真省电"，**必须在同一个进程里先跑 CUDA 再跑 CPU**，或者直接看长时间稳态。
2. 整机功耗（是否 <100 W 供电上限）**仍未直接测量**，需要 USB-C 功率计或 HWiNFO 长时间采样。nvidia-smi 快照已经出现过 590.01 W 的荒谬值，不能用于整机结论。

### 6.4 ⚠️ 实测发现的一个质量问题：sherpa 输出**没有标点**

这是本轮最重要的意外发现。同一段音频：

| 后端 | 输出 |
|---|---|
| FunASR（PyTorch） | 去陈述教育**。**所以教育的陈述方式有这三个方面**。**那其中咱们在考题过程中考的比较多的是教育的定义**，**而且它也 |
| sherpa-onnx int8 | 去陈述教育所以教育的陈述方式有这三个方面那其中咱们在考题过程中考的比较多的是教育的定义而且它也是最难 |

排查过程与结论：

1. **不是词表缺标点**——`tokens.txt` 里 `。`(9730 行)、`，`(24880)、`？`(24884) 都在，25055 个 token 与 FunASR 的 `tokens.json` 完全一致。
2. **不是 `use_itn` 开关**——`use_itn=True/False` 都没有标点。
3. **无法用 beam search 修复**——sherpa 明确报 `Only greedy_search is supported at present`。
4. **根因是 sherpa 的贪心解码 + int8 量化**：标点这类"低置信度但语义重要"的 token 被丢掉。

**解决：在后处理接一个标点模型**（sherpa-onnx 自带的 `OfflinePunctuation`，CT-Transformer）：

- 模型：`sherpa-onnx-punct-ct-transformer-zh-en-vocab272727-2024-04-12-int8`，**75 MB**
- 效果（同一段）：`去陈述教育，所以教育的陈述方式有这三个方面。那其中咱们在考题过程中考的比较多的是教育的定义，而且它也是最难的一个。`
- **与 FunASR 的差距只剩首句处一个标点选择（"，" vs "。"）**，两者都合理。
- 代价：**+75 MB 体积、+15 ms 延迟**。

### 6.5 体积实测

| 组成 | 实测体积 |
|---|---|
| `sherpa-onnx` + `sherpa-onnx-core`（onnxruntime 已静态链接在内） | **19.2 MB** |
| SenseVoice int8 ONNX（`model.int8.onnx` 237 MB + tokens） | 233 MB |
| CT-Transformer 标点模型 int8 | 75 MB |
| **合计** | **≈ 327 MB** |

对比现状（torch + CUDA runtime + funasr + transformers）约 **2.5 GB** → **缩小约 7.6 倍**。

## 7. 「插电 GPU / 离电 CPU」可配置性评估

### 7.1 结论：可行，但有一个硬冲突要先解决

**已有的基础（比预期好）**：

- `asr_device` **已经是运行时设置项**，UI 里有下拉框（`control_panel.py:248`，选项 `cuda` / `cpu`）。
- **`psutil` 已在 requirements 里** → `psutil.sensors_battery().power_plugged` 可直接判断交流/电池，**不需要新增任何依赖**。
- **每个后端都实现了 `to_device()`**（包括 `SenseVoiceEngine.to_device`），具备热迁移模型的能力。

**缺的两块**：

1. `asr_worker.py` 只认 `shutdown` / `transcribe` / `set_language` / `set_input_padding` —— **`to_device` 实现了但没有接到 IPC**。加一个 `set_device` 命令约 15 行。
2. 没有电源状态监听。

**两种切换粒度**：

| 做法 | 代价 | 适用 |
|---|---|---|
| 新增 `set_device` IPC，**同一后端热切设备** | 无 GUI 阻塞、无重新加载；CPU→GPU 首次要建 CUDA context | 同为 PyTorch 后端时 |
| 走现有 `_switch_asr_engine`，**换后端** | 重启 worker：sherpa 约 2 s / PyTorch 约 12 s（有加载对话框） | CPU=sherpa、GPU=PyTorch 时 |

### 7.2 ⚠️ 硬冲突：「轻量打包」与「插电用 GPU」互斥

- lite 包要瘦下来，就必须**剔掉 torch / CUDA / funasr / transformers**；
- 但剔掉之后，**GPU 加速能力也没了**。
- **不可能同时做到「~250 MB 的包」和「插电时用 CUDA」。**

三个可选解：

| 方案 | 说明 |
|---|---|
| **a. 两个发行版** | `lite`（≈330 MB，sherpa CPU）+ `full`（≈2.5 GB，含 CUDA），同一份代码用 `build_exe.py --target {lite,full}` 产出 |
| **b. 只发 lite，放弃 GPU** | 最简单，且实测 CPU 已够快（见下） |
| **c. lite 主体 + GPU 可选组件** | 首次插电时提示下载约 1.8 GB 的 CUDA 运行时包 |

### 7.3 一个需要重新审视的前提

**"插电切 GPU"的收益可能没有想象中大**，理由是实测数据：

- CPU 方案 **230 ms** 已经远低于 600 ms 约束，GPU 的 95 ms 在**用户感知上几乎无差别**（字幕的瓶颈是 VAD 分段与显示节奏，不是这 100 多毫秒）。
- GPU 让 dGPU 长期停在 **P0 / 20.9 W**，而 CPU 是 **P8 / 2.7 W**。
- **GPU 的真正价值不是"让 SenseVoice 更快"，而是"能跑更大的模型"**——例如 FireRedASR-AED（1.1B，中文 CER 3.18%）或 Fun-ASR-Nano（800M）。SenseVoice 在 CPU 上已经跑满它的潜力了。

因此更合理的设计是让插电/离电切换有**真实的语义差异**：

| 电源 | 后端 | 目标 |
|---|---|---|
| 离电 | sherpa-onnx int8（SenseVoice + 标点） | 230 ms / 2.7 W，续航优先 |
| 插电 | 可选的大模型后端（FireRedASR / Fun-ASR-Nano） | 准确率优先，允许吃 GPU |

如果只是"插电让 SenseVoice 从 230 ms 变成 95 ms"，那多出来的 1.8 GB 运行时和 20 W 常驻功耗，性价比很低。

### 8.3 ⚠️ 实测发现并修复的两个问题

**问题 1：sherpa 的语言标记不可靠，且会引发下游 bug。**

5/5 采样点 sherpa 都报 `<|yue|>`，而 FunASR 对**逐字节相同**的音频报 `<|zh|>`。

这不是显示问题而已：`yasbd` **没有 `yue` 分词器**，`_get_segmenter` 会静默回退到 `en`（拉丁断句规则）→ 中文讲稿的断句整体降级为按 60 字逗号切。

两处修复：
- `backends/sherpa_onnx.py`：把 `yue` 归一为 `zh`（同为 CJK、标点相同），**原始标记仍写进 debug 日志**，不丢信息；
- `main.py`：新增 `_SEGMENTER_LANG_ALIASES`，让 `yue` 走 `zh` 分词器——这样即使语言来自别的后端也不会踩同一个坑。

**问题 2（我引入、被验证抓到）：`UnboundLocalError: QCheckBox`。**

`_create_vad_tab` 方法内部第 616 行有一句**局部** `from PyQt6.QtWidgets import QCheckBox`。Python 的作用域规则是"函数内任何位置有赋值/导入，该名字在整个函数内就是局部"，于是我在同方法前面（377 行）用 `QCheckBox` 直接炸掉。删掉那句冗余导入（模块级已有），并留了注释防止被加回来。

> 这也说明了 `tools/verify_ui.py` 的价值——语法检查完全看不出来，只有真正构建面板才会暴露。

**问题 3：`is_asr_cached('sherpa-onnx', 'nope')` 返回 True。** `sherpa_profile()` 对未知 key 会回退到默认配置，导致"配置里写错模型名"被当成"模型已就绪"。改为 `get_sherpa_model_paths()` 对未知 key 直接返回 `None`（并记 warning），`sherpa_profile()` 保持回退只用于显示。

## 9. P2 实施记录：VAD 迁移（2026-10-11 完成）

目标：把最后一块 torch 依赖（`silero_vad`）从采集路径上摘掉。

### 9.1 ⚠️ 关键发现：**不能直接用 sherpa 自带的 VAD 模型**

第一直觉是"既然都用 sherpa-onnx 了，就用它的 `VoiceActivityDetector`"。但实测下来两步都踩了坑：

**坑 1：模型版本不同。** sherpa 自带的 `silero_vad.onnx`（643 KB）是 **v4**（LSTM hidden **64**），而 `silero-vad` PyPI 包是 **v5**（hidden **128**）。两者逐窗口概率的相关性只有 **0.72**、最大差 **0.98** —— 换过去会**改变分段行为**，不是"换运行时"。

**坑 2：正确的模型在 silero-vad 包里。** `site-packages/silero_vad/data/` 下有官方导出的多种 ONNX（`silero_vad.onnx` 2.3 MB、`_16k_op15`、`_half`、`_openvino_16k` 等）。用其中的 **v5** 才与现有行为同源。

**坑 3（最容易错）：输入要先拼 64 样本的 context。** 参考官方 `silero_vad.utils_vad.OnnxWrapper` —— 模型期望的输入是 **576** 样本（上一窗口尾部 64 + 当前 512），并需把 LSTM state（`[2,1,128]`）逐次透传。**只喂 512 会让每个窗口都返回 ~0.0（"静音"）**，我第一次就是这么错的，而且它不报错，只是静默地全判静音。

修正后：与 torch 版逐窗口概率 **max abs diff 2e-6、corr 1.000000**（真实课堂音频，两个采样点）。

### 9.2 改了什么

| 文件 | 改动 |
|---|---|
| `livetranslate/audio/vad.py` | `import torch` 改为可选；新增 `_SileroVadOnnx`（官方 `OnnxWrapper` 的直接移植，含 context 拼接与 state 透传）；新增 `_load_silero_model()`，**优先 ONNX、回退 torch**；`_silero_confidence()` 按运行时分派 |
| `livetranslate/models/manager.py` | 登记 `models/silero_vad.onnx`；`is_silero_cached()` 优先检查 ONNX 版；`download_silero()` 先看 ONNX，避免在无 torch 环境里 `import torch` 失败 |
| `main.py` | 顶层 `import torch` 改为 try/except；两处 `torch.cuda` 调用加 `torch is not None` |
| `models/silero_vad.onnx` | 新增（2.3 MB，随包分发） |
| `tools/verify_vad_onnx.py` | **新增**。对比两种运行时的分段与每块开销 |

> **为什么不用 sherpa 的 `VoiceActivityDetector`**：那是另一套分段状态机，会绕过本项目积累的全部调优（渐进静音、自适应停顿阈值、`max_speech_duration` 时的最佳停顿点回切、语音密度过滤）。这些逻辑全都建立在**逐块连续置信度**之上，而高层 VAD 只吐语音段、不给置信度。所以正确做法是只替换**置信度计算**这一层。

### 9.3 验证结果

| 验证 | 结果 |
|---|---|
| **分段一致性**（真实课堂 40 s） | onnx 与 torch **完全相同**：`[3.74, 5.6, 2.78, 6.37, 6.05, 2.4, 5.06, 7.07]` |
| **每块开销** | onnx **0.13 ms** vs torch 0.37 ms（**快 2.8 倍**），预算 32 ms |
| **无 torch 环境** | 用 `meta_path` hook 禁掉 torch：VAD 自动走 ONNX、`available_backends()` 只剩 `('sherpa-onnx',)`、`import main` 成功、**全程 torch 从未被导入** |
| `verify_ui.py` | 16/16 通过 |
| `verify_runtime.py` | 9/9 通过 |
| `pytest tests/` | 73 passed |

### 9.4 torch 依赖现状（GUI 路径已清零）

剩下的 torch 引用全部在**不会被执行的位置**：

- `ui/overlay.py`、`ui/control_panel.py`、`asr/worker.py` 里的 `import torch` 都在 `try/except` 内；
- `asr/backends/sensevoice.py` / `funasr_nano.py` / `anime_whisper.py` / `nano_src/` 是 torch-based 后端，由 registry **惰性加载**，只有用户选中它们时才会 import torch；而在 CPU-only 构建里它们不会出现在引擎下拉里（`available_backends()` 已过滤）。

**结论：P3（CPU-only 打包）的代码前提已经具备。**

## 10. P3 实施记录：CPU-only 打包（2026-10-11 完成）

### 10.1 产物

| | 数值 |
|---|---|
| `LiveTranslate.exe` | **92.8 MB**（旧的带 PyTorch 版 **2.8 GB**，缩小约 30 倍） |
| `LiveTranslate-20261011-win64.zip` | **309.9 MB**（exe + config.yaml + models/ 310MB） |
| 首次启动 | **< 1 秒** |
| 运行时依赖 | **`torch installed: False`** —— 打包产物里真的一行 torch 都没有 |

`build_exe.py` 新增：`--with-torch`（切回完整版；默认 lite）、`--package`（构建后打 zip）、`--package-only`（只打 zip，省 3 分钟）。

lite 模式排除 torch / torchaudio / torchvision / funasr / ctranslate2 / faster_whisper / transformers / tokenizers / safetensors / modelscope / huggingface_hub / silero_vad，**以及 librosa / soundfile / audioread**——librosa 会拖进 numba、llvmlite、scipy 上百 MB，而采集路径只见 16kHz 原始 PCM。

### 10.2 ⚠️ 五个坑（每一个都会让"看起来正常"的包在用户手里失败）

**1. `ImportError: DLL load failed while importing _ssl`**（第一次发布就被撞上）

conda 把 CPython 扩展依赖的 DLL 放在 `Library/bin/`，**PyInstaller 的依赖遍历不看那里**。崩溃链路：`main → translator → openai → anyio → ssl`。
修法：收集 `<sys.prefix>/Library/bin/*.dll`——**总共 21MB / 69 个文件**，排除 `ucrtbase.dll`（系统自带，打包会冲突）与 tcl/tk（已 exclude）。

**2. `AttributeError: 'NoneType' object has no attribute 'exists'`** —— 当天第三次撞同一个 Python 作用域陷阱

`dialogs.py` 自己有一句 `SETTINGS_FILE = None`（上游留给 control_panel 稍后注入），把 `import` 进来的名字**整个模块覆盖成 None**。
修法：改用别名 `from livetranslate.paths import SETTINGS_FILE as _SETTINGS_PATH`，并在该赋值处加注释警告。

> 三次的形态一致：**函数内（或模块内）任何位置的赋值/导入，都会让那个名字在该作用域内变成局部**。代码检查工具看不出来，只有真正执行才炸。

**3. 向导硬编码 `"asr_engine": "funasr"`**

后果链：exe 读 `config.yaml` 得到 sherpa-onnx → 向导写出的 settings 却是 `funasr` / `sensevoice-small`，且 sherpa 三个字段全部丢失 → 下次启动判定"缺少 SenseVoice Small" → 弹下载框 → `No module named 'modelscope'` 崩。
修法：新增 `_config_asr_defaults()`，从 `config.yaml` 读默认值来 seed 向导，不再硬编码。

**4. `main.py` 的模型键解析没覆盖 sherpa**，且 sherpa 缺模型时会弹一个**必然失败的下载框**（模型随包分发，根本不走网络）。
修法：补 sherpa 分支；sherpa 缺模型改为记 ERROR 并继续（让引擎自己报精确错误），不弹框。

**5. ⚠️ 最严重：backend 模块根本没进包**

用户双击 exe → 走完初次配置 → 报 **`ASR 模型加载失败: No module named 'livetranslate.asr.backends.sherpa_onnx'`**。

根因：`registry.py` 用 `importlib.import_module("<字符串>")` 解析引擎，**PyInstaller 的静态依赖遍历看不见**。只把 `livetranslate.asr.backends`（包）写进 hiddenimports 不够——它的 `__init__.py` 是空的，不 import 任何子模块。分析结果里 backend 一个都没进去。

修法：把所有 backend 模块显式列入 hiddenimports（lite 加 `sherpa_onnx` + `remote`；`--with-torch` 另加 `funasr`/`sensevoice`/`funasr_nano`/`anime_whisper`/`whisper`）。

> **这条的教训比 bug 本身重要**：我之前"验证通过"只证明了**它能启动**。而用户的第一个真实动作是**加载模型**，恰好是唯一没被验证的路径。**"能启动"不是发布标准。**

### 10.3 新增：`--selftest` 自检开关

为了让上面那条不再重演，`main.py` 增加了无头自检：

```
LiveTranslate.exe --selftest      # 退出码 0 = 通过
```

它报告 torch 是否存在、可用引擎、VAD 是否就位、**真的启动一次 ASR worker 并转写一段静音**；结果同时写入 `logs/selftest.log`（one-file exe 是 windowed，看不到 stdout）。

发布前实测：

```
torch installed    : False
available backends : ('sherpa-onnx',)
silero VAD on disk : True
engine to load     : sherpa-onnx
worker ready       : {'engine_type': 'sherpa-onnx', 'device': 'cpu'}
transcribe(silence): {'text': '嗯。', 'language': 'zh'}

```

**从干净的 release zip 解压到全新目录后运行同样通过**——这才是可以发布的证据。

### 10.4 首次启动的 15 秒白等

SetupWizard 有个"15 秒后自动开始下载"的倒计时；模型已随包分发时它纯属干等，读起来像卡死。修法：`__init__` 里预检模型，已就绪就 `QTimer.singleShot(100, self._start_download)`。启动时间 15s → **<1s**。
